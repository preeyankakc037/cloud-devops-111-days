# Day 107 – Terraform State, Remote Backends & Team Workflows

## Overview  
Today I went deeper into Terraform by focusing on one of its most critical components: **state management**. I also explored how teams use remote backends to collaborate safely on infrastructure.

## My Understanding  
Terraform uses a **state file** to keep track of the current infrastructure. This state is what allows Terraform to understand:
- What already exists  
- What needs to change  
- What should be created or destroyed  

In real-world environments, managing this state properly is extremely important.

## What I Did  

I learned how local state works and why it is not suitable for teams. Then I explored remote backends like AWS S3 to store the state file securely.

I also understood how **state locking** prevents multiple people from making changes at the same time, avoiding conflicts and infrastructure corruption.

## Key Concepts  

State File (`terraform.tfstate`)  
Stores the current state of infrastructure.

Remote Backend  
A shared location (like S3) to store state for team access.

State Locking  
Prevents simultaneous updates to infrastructure.

Drift Detection  
Identifying changes made outside Terraform.

## Real-World Workflow  

- Store state in S3 (remote backend)  
- Enable state locking (DynamoDB)  
- Use `terraform plan` before every apply  
- Avoid manual changes in cloud console  

## Key Insight  

State is the **single source of truth** in Terraform.  
If state is lost or corrupted, infrastructure management becomes difficult.

## Reflection  

This topic made me realize that Terraform is not just about writing configs—it’s about managing infrastructure safely at scale, especially in team environments.
